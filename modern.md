# modern.md — how the generated Java reads against `java.md` and `backend.md`

What is left of the assessment: **eight defects that survive a perfect field
spec.** Everything that turned out to be an input problem — a manifest that
named a column `time_stamp`, or asked for no indexes — is deleted, along with
everything that shipped. `git log -p -- modern.md` is the record.

**A closed entry is deleted from this file, not marked done.** Section numbers
are stable and never reused, so a `modern.md §11.1` citation in the source
still resolves to a subject.

Every entry below was **re-confirmed on 2026-08-27**, and again the same day
after `--set`, `--via`, `--if-match`, `--bind` and `g scaffold --path` shipped:
none of those touched any of the eight. The project is built from nothing but

```sh
jails new --offline m --package com.example.m && cd m
jails add db --no-start
jails g scaffold User    id:uuid@pk email:string@unique
jails g scaffold Message id:uuid@pk userId:uuid content:string isRead:boolean
jails g query MessagesForUser --on Message userId:uuid --path '/admin_api/messages/{userId}'
jails g usecase EnsureUser --on User email:string --on-conflict email
jails add cors observability
jails add kafka --no-start
jails g event MessagePosted id:uuid content:string
```

so none of them is a property of one manifest.

## 4. Migrations

### 4.3 No index serves any query the application runs

`g query MessagesForUser --on Message userId:uuid` generates an adapter that
runs `where user_id = :user_id order by id limit 100`. The table it reads was
generated by `g scaffold Message` two commands earlier:

```sql
create table messages (
  id       uuid    not null,
  user_id  uuid    not null,
  content  text    not null,
  is_read  boolean not null,

  constraint messages_pk
    primary key (id)
);
```

No index on `user_id`. Every lookup is a sequential scan and a sort, and jails
does not mention it. `--index` exists and the shape is one jails can see: a
`query --on X` whose filter columns carry no index is exactly the kind of thing
the `free-text-closed-set` warning already reports for the closed-set case.

## 5. Type modelling

### 5.4 Boxed primitives on the wire

The domain record is right:

```java
public record Message(UUID id, UUID userId, String content, boolean isRead)
```

The generated response boxes it:

```java
public record MessageResponse(UUID id, UUID userId, String content, Boolean isRead)
```

`null` becomes representable in a field describing a `boolean` that cannot be
null, and the request record boxes it too and then `@NotNull`s it — the
validation annotation compensating for the wrong type. The mapping between the
two is generated from one field spec, so the two renderings disagree with
nothing in between to notice.

## 6. Architecture — the layering the comments describe is not the layering that exists

### 6.3 `AppMetrics`, `CorsConfig`, `MetricsConfig` land in the root package

```
src/main/java/com/example/m/AppMetrics.java
src/main/java/com/example/m/CorsConfig.java
src/main/java/com/example/m/MApplication.java
src/main/java/com/example/m/MetricsConfig.java
```

Three configuration classes sit beside `@SpringBootApplication` while every
generated *kind* goes through `generate::layout` to the subpackage its layer
owns. A capability's files decide nothing, so they land where nothing put them.
`config::LAYERS_IN_ORDER` has eleven layers and none of them is claimed here.

### 6.4 Interfaces with one implementation, and a service that forwards

`MessageService` is four methods, each one line:

```java
public List<Message> findAll()            { return repository.findAll(); }
public Optional<Message> findById(UUID id) { return repository.findById(id); }
```

`java.md` §8: *"Interfaces are extracted when there is a second implementation
or a test seam you actually need — not reflexively."* The port has a real
second implementation (the in-memory fake), so the port earns its place; the
service between the controller and the port does not.

### 6.5 Two API styles in one service

Every route in the project above:

```
/users                            /messages                       (REST, scaffold)
/admin_api/messages/{userId}      /customer_api/messages          (--path, explicit)
/actions/ensure-user                                              (RPC-over-POST)
/admin_api/unread2                                                (POST, to read)
```

REST for the scaffold and RPC-over-POST for the generated operations, in one
service, chosen by which command wrote the route rather than by a decision.
A `POST` to read is uncacheable, unlinkable and unloggable by URL.

**Half of this closed and the half that matters did not.** `g scaffold --path`
is accepted now, so a project *can* be made consistent -- the sentence that
used to stand here, that it could not be without hand-editing the controller
jails had just written, is no longer true. What is left is the default: the
two styles are still chosen by which command wrote the route, so consistency
is something the reader has to know to ask for, on every command, rather than
something the tool has an opinion about. A default that is right half the time
is the thing this entry is about.

## 7. The HTTP contract

Two defects in the read and command endpoints, both reproduced above:

- **The criteria record is bound directly as `@RequestBody`.**
  `UnreadTwoQueryController` takes `@Valid @RequestBody UnreadTwoCriteria` —
  the service-layer type, on the wire — while `MessageRequest`'s own Javadoc in
  the same project argues at length that the wire type must not be the domain
  type. The rule is stated in one generated file and broken in the next.
- **`MAX_RESULTS = 100`, applied silently.** No cursor, no total, and nothing
  in the response says the list was truncated. The cap is documented only in
  the adapter's own Javadoc — *"Equality queries are deliberately bounded"* —
  which the caller never sees. A caller receiving 100 rows cannot tell whether
  there were 100 or ten thousand.

## 8. The generated Kafka listener is a `TODO`

```java
private static final Logger log = LoggerFactory.getLogger(MessagePostedListener.class);

log.info("received {}", event.id());
// TODO: hand this to the application service that owns the reaction.
```

It logs an id and drops the event, under a Javadoc that says *"it hands the
event to the application and does nothing else"*. It does the second half. The
reasoning above it is right — business logic in a listener is unreachable from
any test that does not start a broker — and there is nowhere for the reaction
to go, because `g event` generates a publisher, a payload, a config and a
listener, and no port for the listener to call. Shipped as is, a project
consuming a topic discards every message on it and logs that it received them.

The purest form of the failure this whole file is about: generated prose
asserting what the generated code does not do.

## 9. Tests

**They mostly test the framework, or nothing.**

- `MessageServiceTest` stubs the port to return empty and asserts the service
  returns empty. The service is a one-line forward (§6.4). The test can only
  fail if Mockito breaks.
- The generated association IT queries `pg_constraint` and
  `unnest(conkey, confkey)` to assert that PostgreSQL recorded the foreign key
  the migration two files away declared. It tests Flyway and PostgreSQL.
  `backend.md` §3: *"Don't test … Spring's wiring. Test the behaviour you'd be
  embarrassed to break."*
- Every fixture value is `"sample"`, in the domain test, the controller test
  and both integration tests, so a `string!` component costs nothing to get
  wrong.
- **Missing entirely: a concurrency test for the `transition` CAS** — the one
  behaviour the `version` column exists for, and the thing jails claims over
  Rails and Django.

Two things the generated tests get right and are worth not losing:
`MockMvcTester` with AssertJ (no `throws Exception`, no two families of static
imports), and containers as `@Bean`s with `@ServiceConnection` rather than
`@Container` statics.
