# Phase 1 test/run loop baseline — 2026-08-26

This is the dated reference-fixture baseline for the Phase 1 exit gate. It does
not claim a general speedup and does not combine resident test execution with
application or container cold start.

## Environment and method

- Commit: `f139a887c930c31409b951a07a8c8eabc8ad44e9`
- Host: Linux `7.1.3-201.fc44.x86_64`, x86_64
- Rust: `rustc 1.97.1 (8bab26f4f 2026-07-14)`, LLVM 22.1.6
- Java: OpenJDK 26.0.2+10-55
- Maven: Apache Maven 3.9.16, ordinary Maven rather than mvnd
- Fixture: `tests/fixtures/benchmarks/phase1-loop`, one main class and three
  eligible JUnit Jupiter test cases
- Samples: 20 per metric; nearest-rank percentiles; debug Cargo integration-test
  binary

The fixture copy, Maven build prime, resident-daemon prime, and direct-launch
classpath/compile prime were outside timed intervals. No container, network
service, or application dependency started in a timed interval. Every lifecycle
sample started a new jails process and a new direct JVM. Warm test samples reused
the resident test daemon and current compiled classes.

Reproduce with:

```sh
JAILS_BENCH_SAMPLES=20 cargo test --test baseline record_phase1_loop_baseline -- --ignored --nocapture
```

## Invalidation and fallback boundary

These warm figures apply only while the test protocol, selected JDK, runtime
classpath, compiled outputs, and isolation classification remain current. The
engine reports why it widens or delegates instead of folding those paths into
the resident numbers:

- changed build inputs, classpath, selected JDK/release, test-engine protocol,
  or class bytes recycle or invalidate the resident engine;
- stale sources are repaired by the selected compile owner, while
  `--compile none` refuses instead of compiling implicitly;
- integration/database/Spring-context tests, global system properties,
  unsupported dynamic selection, and other isolation uncertainty delegate to
  the ordinary build engine in auto mode and refuse in strict warm mode;
- ambiguous main class, stale/missing runtime output, unsupported bytecode, or
  a cache fingerprint mismatch refuses direct launch with the explicit
  `--launcher build-tool` diagnostic fallback;
- watcher overflow, daemon failure, sequence/epoch mismatch, and application
  failure terminate or recycle owned processes rather than returning a
  plausible stale result.

Build fallback, recompilation, daemon recycle, build-tool launch, and service or
container startup are intentionally not presented as warm-loop measurements.
They are correctness paths with visible reasons and materially different work;
combining them would make both the latency claim and the fallback behavior less
truthful.
